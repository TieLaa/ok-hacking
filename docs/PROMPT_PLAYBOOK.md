# 提示词手册（新项目开场 / 中途纠偏）

> 用途：下一个游戏自动化项目启动时，直接复制这里的模板，避免重复踩本项目的坑。
> 每次踩到新坑，先问「当时哪句话没写，才会让 agent 走错」——补到对应小节，不要只补代码。

## 0. 一句话原则

**在提示词里写清「边界」和「验收」，比写清「要做什么」更重要。**
agent 不缺执行力，缺的是「什么不许做」「怎么算做完」。

## 1. 新项目开场模板

```text
目标：给 <游戏> 做 <范围> 自动化，框架用 ok-script（版本锁 requirements.txt）。

先做环境确认，不要写业务代码：
1. 读 <模板仓库> 的 config.py / BaseTask 用法，列出接入点；
2. 确认游戏进程名、窗口类、客户区分辨率、是否管理员权限；
3. 用 tools/ 下的抓图脚本验证能稳定出帧（窗口部分可见即可，不要最小化）；
4. 把上述事实写进 docs/ENVIRONMENT.md，再开始写任务。

硬约束：
- 路径纯英文，Python 3.12 venv；
- 没有实测过的结论，标注「待验证」，不要写成事实；
- 每完成一个可验证成果就 commit 一次，不要攒着。
```

**为什么**：本项目开局就卡在「游戏是管理员进程」和「窗口被遮挡 WGC 无帧」，这两条都是环境事实，不是代码问题。先落 `docs/ENVIRONMENT.md`，后面每个会话都能查。

## 2. 加界面前（最常用）

```text
加一个界面：<界面名>。
证据：截图在 <路径>，OCR 文字在 <同目录 ocr.txt>（先读文字，不要直接读图）。
要求：
1. 先跑 tools/check_handlers.py <图> --cache --verbose，确认现有 handler 没认走；
2. 判据只用这个界面独有的文案/区域，写进 docstring 说明为什么不用别的词；
3. handler 放进 <域>.py，并在 handlers/__init__.py 里说明为什么放这个位置；
4. 更新 expected.json，全量回归必须 exit 0；
5. 一个界面一个 commit。
```

**为什么**：不写「放哪个位置」和「为什么」，agent 会把新 handler 追加到末尾，被前面的宽松判据吃掉，表现是「改了但没生效」。

## 3. 改判据 / 修 bug 前

```text
先复现，再改。
1. 从 logs/debug/<时间>_<tag>/ 读 ocr.txt + actions.txt，指出卡在哪一步、哪个 handler 命中；
2. 如果是 OCR 漏判，再读 frame.jpg（最多 1 张）；
3. 改完跑 tools/check_handlers.py --cache，贴出 exit code 和差异行；
4. 回归没通过不许说「修好了」。
```

**为什么**：本项目最常见的返工是「凭印象改判据，结果别的界面被抢」。回归断言是唯一能兜住的东西。

## 4. 读图约束

```text
这个会话最多读 3 张图。优先读 ocr.txt / actions.txt。
必须读图时：只读与当前问题相关的那一张，读完在回复里写一句「从图里看到了什么」，
不要连续贴多张 1080p 截图。
```

**为什么**：1080p 图每张约 1 MB（JPEG），历史图每轮重发，实测 19 张图把每轮从 5 秒拖到 90 秒。

## 5. 重构前

```text
先 commit，再重构。
1. 保存重构前的回归基线（check_handlers.py --cache > baseline.txt）；
2. 只搬代码不改行为；
3. 重构后逐张对比命中结果，有差异必须解释；
4. 重构和功能改动分成两个 commit。
```

**为什么**：本项目 2117 行单文件拆分时，漏搬了类级常量 `W_MATE`，回归立刻抓到 `subject-crit` 未命中。没有基线就只能靠猜。

## 6. 改完怎么验证（MCP 循环）

```text
改完任务后不要重启 GUI，按这个顺序验证：
1. tools/check_handlers.py --cache，exit 0（识别层，秒级）；
2. list_tasks 拿到 task_id 和源码路径，确认你改的是同一份文件；
3. reload_tasks(task_ids=[...])，轮询 get_run_status 到 succeeded；
4. run_task 提交 tools/mcp/probe.py（先确认大厅/OCR/顶栏），再提交对应 smoke；
5. 失败先读 logs/mcp/<run_id>/ 的 status.json + run.log + 产物图，再改代码。
注意：改了 src/tasks/training/ 下被 import 的模块（parsers/handlers/flow）必须重启
runtime，reload_tasks 只刷新已注册任务模块。
```

**为什么**：不写这条，agent 会「改完直接说好了」；或者把 TrainingTask 整段复制进临时脚本验证，验证的是一份克隆而不是真实实现。

## 7. 配置类问题
```text
改行为前先确认三处：
1. 代码里的 default_config / config.get 默认值；
2. configs/<Task>.json 里用户已有的覆盖值；
3. configs/devices.json 是否覆盖了交互方式。
```

**为什么**：「改代码默认值对已存在的 json 无效」这个坑，本项目在「周末允许进步行街」上踩过一次，表现为「代码明明改了，运行时还是去公园」。

## 8. 交接模板（换会话 / 换 agent 时用）

```text
交接：<任务名>
目标：
现状（已验证 / 未验证分开写）：
下一步（按顺序，可执行命令）：
涉及文件：
现场状态（游戏停在哪、配置关键项）：
不要做什么：
```

**为什么**：交接里写「不要做什么」比写「要做什么」更能防止下一个 agent 乱动。

## 9. 反面示例（这些话会直接导致返工）

| 不要这样说 | 改成 |
|---|---|
| 「把 XX 修一下」 | 「XX 的现象是 A，预期是 B，先复现再改」 |
| 「顺手优化一下」 | 「只改 XX，其他保持不动」 |
| 「加个 handler」 | 「加 handler，说明判据和插入位置，并更新 expected.json」 |
| 「应该没问题吧」 | 「跑回归，贴 exit code」 |
| 「读一下这些截图」 | 「先读 ocr.txt，需要时最多读 1 张图」 |
| 「重构一下代码」 | 「先 commit，存基线，只搬不改，回归对比后再说」 |

## 10. 每次新坑补一条

格式：

```text
### <坑的名称>
- 现象：
- 根因：
- 提示词里应该加的那句：
```

### 重构后文件相对路径偏移

- 现象：日志说「存证 logs/unknown/xxx.jpg」，但 `logs/` 里没有文件。
- 根因：用 `dirname(__file__)` 数层数找项目根；文件从 `src/tasks/` 移到 `src/tasks/training/` 后少算一层，写到了 `src/logs/`。
- 提示词里应该加的那句：**「重构搬文件后，所有基于 `__file__` 的相对路径都改成统一的 `PROJECT_ROOT` 常量。」**

### 兜底点击不参与卡死检测

- 现象：不认识的界面一直点屏幕中央，既不 debug 也不停，最后耗光操作数。
- 根因：卡死检测只在 handler 命中时记录「点击后指纹」，兜底分支没记，`_no_change` 永远是 0。
- 提示词里应该加的那句：**「兜底路径也必须记录点击后指纹，和 handler 路径共用同一套『3 次无变化』判定。」**

### 放宽判据会抢已有界面

- 现象：为让事件三选一识别《书名号》选项，放宽了长度和字符限制，结果剧情三选一被同一 handler 抢走。
- 根因：两个界面 UI 完全一样（三个白底横条 + 右上跳过），只能靠文字特征区分。
- 提示词里应该加的那句：**「放宽 handler 判据后必须跑全量回归；如果两个界面 UI 相同，先确认它们的行为是否应该一致，再决定是改判据还是改期望表。」**

### 二级确认页

- 现象：点完「划船」后停在详情页，每拍点中央都没反应。
- 根因：地点详情是二级确认（「前往划船」），旧流程只处理了第一级。
- 提示词里应该加的那句：**「加地点/活动 handler 时，先确认是一级还是两级确认（选择 → 前往XXX）。」**

### 一键启动脚本误点别的任务卡

- 现象：`tools/start_ok_task.py` 报「已排队」，跑的却是 `Configuration Demo Task`；OK 窗口里任务卡有 4 张，日志都打 `queued onetime_task`。
- 根因：脚本只判断「有没有排上队」，不核对任务名；OK 刚启动头几秒点击还会被吞，候选 y 逐个试时越试越往下，最后停在示例卡。
- 提示词里应该加的那句：**「点任务卡必须核对日志里的任务名（`训练循环`/`TrainingTask`），排错了要报错退出，不能当作成功。」**

### F8 轮询误报把任务停掉

- 现象：无操作时任务突然报「按下 F8（轮询兜底）→ 请求停止」。2026-10-27 首尾两局各一次。
- 根因：`GetAsyncKeyState` 单拍采样就判定按下，手柄/输入法/其他软件转发的瞬时状态也会命中。
- 提示词里应该加的那句：**「轮询按键必须连续 N 拍确认（本项目 3 拍 ≈150ms），单拍只记 debug。」**

### 信息栏被当成「竖向三选一」

- 现象：QuickMatch 挂在全国大赛关卡列表，每 0.5 秒点一次「对手实力」，点了 30 秒没反应，最后因为切窗口才被前台检查拦下。
- 根因：`choice_candidates` 只按「屏幕中部 + 同列竖排 + 短文本」判形态，关卡详情页右侧的「对手实力／关卡加成／奖励预览」、周结算页左列的「控卫／分卫／小前／大前／中锋」、周末前对话字幕「我要去和小式一起去看电影」都完全符合；TriggerTask 又没有看门狗。
- 提示词里应该加的那句：**「竖向选项是**居中一列**（实测 cx≈0.50）：候选先收窄到 0.38~0.62 再判形态，贴边的一列几乎都是表格列或字幕；组内项数只能 2~3。不要靠文字里有没有符号去排除——台词里什么符号都会出现。」**

### 常驻任务（TriggerTask）没有任何防重复点击

- 现象：判据一误命中，TriggerTask 就每 0.5 秒点同一处、永不停止，只能靠人发现。
- 根因：`_no_change` 看门狗只在 TrainingTask 的 flow 里，TriggerTask 没有。
- 提示词里应该加的那句：**「常驻任务必须自带『同一画面指纹连点 N 拍就存证+停手 N 拍』的保护，比赛内 HUD 这类本来就该连点的 handler 要豁免。」**

### 抽卡页动画期间的 OCR 结果不能直接采信

- 现象：扭蛋页卡片还在飞入/翻转时也能读出 3 张卡，脚本 0.3 秒就点「确定」，买下中间那张紫卡；1.7 秒后重进才看清同价位的金卡（防守增加++ / 80 币），等于白扔一次机会。
- 根因：`read_gacha_cards` 只靠「价格数字 + 卡名位置」定位，动画中间态同样满足；旧代码只处理了「读不到卡」这一种情况，读到但可能还在动的情况没管。
- 提示词里应该加的那句：**「抽卡/翻牌页必须先确认卡片稳定（连续两帧识别一致）再决策——『读不到』和『读到了但还在动』是两回事。」**

### 科目名被吞进旁边的「MAX」标签

- 现象：2026-10-29 第 4 周海边合宿星期三，日志候选科目里明明有「防守（小人）」，但整轮只探测了弹跳和运控，防守一次都没点；用户看到的是「有队友的防守训练被跳过了」。
- 根因：满级科目的按钮是「名字 + MAX」，OCR 把「守」和 MAX 糊成一个框，这一帧只剩「防」；`subjects_from_texts` 只会把**两个单字**拼回科目名，少一个字就返回空，`find_subject_box` 拿到 None 后 `continue`，**静默跳过，日志里连一行都没有**。
- 提示词里应该加的那句：**「OCR 对按钮文字的漏读要按『已知词表』补全：六个科目的首字/尾字都唯一，只剩一个字也能定位那一行；任何『找不到就 continue』的分支必须打告警，不能让科目静默消失。」**

### 购买次数不能当上限

- 现象：2026-10-29 游戏厅买了 237 次同一个「防守」小游戏，卡了 9 分钟，任务还停不下来。
- 根因：`handle_arcade` 没有「这一下到底成交没成交」的判断，零用钱读不到（`None`）时还被当成买得起；而卡死看门狗靠界面指纹，金额数字每拍都在变，签名一直变，永远判不出卡住。
- 提示词里应该加的那句：**「购买类流程不许用『一天买几次』当上限（羽漱川湊能买两次、卧云真昼能买升级版、白神时久有免费商品）；要判『成交没成交』——成交必然改变页面状态（零用钱变少/卡片消失），连续 N 次零用钱没变且还是同一件才算点不动。」**

### 「让路暂停」和「Alt 抢前台」不能同时成立

- 现象：2026-10-29 第一版「键鼠暂停」写完，用户反馈「还是抢鼠标」——暂停 5 秒到点后第一个动作就是 Alt 抢前台，人刚停手就被踢下焦点。
- 根因：本游戏只吃真实鼠标事件（`PostMessage` 实测无效），要点击就必须先把游戏置前，而置前就是拿走用户焦点。「暂停 N 秒」只是把「抢」往后推，不是不抢。
- 现在的做法：只看「用户最后一次输入距今多久」，静默满 3 秒才动手（配置项「空闲等待(秒)」）；**没有等待上限**，旧实现的 120 秒兜底会去抢正在操作的用户。Alt 注入本身也是系统输入事件，`ensure_foreground` 里必须 try/finally 记账，否则下一次动作会把脚本自己的 Alt 当成「用户还在操作」。
- 提示词里应该加的那句：**「让路类需求不许用『暂停 N 秒』实现，要改成『用户静默满 N 秒』；任何抢前台/注入输入的分支都必须纳入同一套记账，且不许设『等太久就强制恢复』的上限。」**

### 框架传参单位：task.swipe 的 duration 是毫秒

- 现象：2026-10-30 选队长翻页每次卡 6 分 42 秒，两次日志精确到 402 秒。
- 根因：ok/task/task.py 的 swipe(duration=0.4) 先算 ms = int(duration*1000) 再传给输入后端，而自定义的 GirlsInteraction.swipe 把第 5 个参数当**秒**用：12 步 × (400/12) 秒 = 400 秒。同一个仓库里 	ools/collect_ssr.py:Screen.swipe 直接调 mouse_event、不经过框架，所以「那边拖动正常」。
- 提示词里应该加的那句：**「自定义输入后端的方法必须和框架调用点对齐单位（毫秒/秒/秒×1000）；凡出现『同一操作某处慢、某处正常』，先拉出两条调用链看谁在做换算，再怀疑算法本身。」**

### 图像判据：纯占比会被零散噪声顶过阈值

- 现象：2026-10-30 周末地图，步行街上方其实没有队友气泡，但建筑阴影的深色像素占比 0.019 贴着 0.02 阈值，某一帧过线 → 判成「步行街和游戏厅都有队友」，按顺序选了没队友的步行街。
- 修法：enue_has_mate 增加「最大连通块占 ROI ≥ 0.05」（气泡是整块 0.12，阴影零散 0.018），并加色相约束（蓝紫 >=r 且 g<=b，排除绿色树影）。同一帧三处地点 0.12/0.15/0.018/0.000，分离度 6 倍。
- 提示词里应该加的那句：**「用像素占比判断『画面上有没有某个 UI 元素』时，必须再加形状约束（最大连通块、长宽比、边缘），否则阴影/高光/贴图噪声会在阈值附近随机翻转；阈值要落在实测两类样本的中间，并在注释里写清样本值。」**

### 顶栏数字「读不到」= 依赖它的判据全部静默失效

- 现象：2026-10-31 餐厅打工，顶栏实际是 23/130，日志里一直是 `精力 None`；
  写好的规则「精力不够右边那张（25）→ 改选左边不耗精力的」从来没生效过。
  同一条链上的扭蛋「清空精力」阈值、公园「野餐」阈值也一直是瞎的。
- 根因：`top_bar()` 是对**裁剪后的顶栏图**再 OCR。同一帧整帧 OCR 读到 `0/130`，
  裁剪重 OCR 读成 `301130` —— 斜杠被吃掉，`STAMINA_RE` 要求有 `/`，于是 None。
- 修法：`top_bar(texts=None)` 优先复用**整帧** OCR（`flow.run()` 存 `_tick_texts`），
  只按 top_bar 区域过滤；裁剪重 OCR 只当兜底。
- 提示词里应该加的那句：**「同一个数字既要 OCR 读得到又要正则匹配得上的时候，
  不要为了省时间去裁剪区域重新 OCR —— 小图上分隔符（`/` `-` `.`）最容易被吞掉；
  优先复用整帧 OCR 结果再按区域过滤。并且凡是 `xxx is None` 都要当告警打出来，
  否则依赖它的规则会静默失效，日志上看只会觉得『规则没生效』。」**

### 二级确认页上的「前往XXX」可能是灰的，不能连点

- 现象：2026-10-31 餐厅，弹窗写着「精力不足 ⚡25」，「前往当服务员」是灰的；
  旧 `handle_activity_go` 无条件点，连点 4 分钟（100+ 次）。
- 为什么全局防卡死没救下来：`_no_change` 按**整页指纹**算，而 OCR 每拍都有细抖动
  （同一个气泡被读成「推荐❤体能 / 推荐体能」）→ 计数被反复复位，
  连「3 轮点不动就停任务」都没触发。
- 修法：`handle_activity_go` 两级判据 —— 按钮附近有「精力不足/无法选择/不可」→ 不点；
  同一个「前往」点过一次画面文字没变 → 不点。两种情况都关掉弹窗、
  把这张卡记进 `blocked_activities()`（当天不再选），回卡片页改选另一张。
- 提示词里应该加的那句：**「点『前往/确定/开始』这种『进入游戏』的按钮之前，
  必须先读按钮附近的『不足 / 不可 / 未满足』提示；同一个按钮连点两次画面没变化
  就要换策略（退出 → 改选），不要指望全局卡死检测 —— 它按整页指纹算，

### 2026-11-02 补充：上次只拆了文案，判据还串着 —— 「互不带动」是判据问题，不是文案问题

- 提示词里应该加的那句：**「『互不带动』不是把按钮文案拆开就完事 ——

### `task.unpause()` 是「停某个任务」按钮里的毒药

- 现象：第一栏点【停止】（断开游戏）后，再点第二栏【暂停】，第一栏自己跳回【停止】。
- 根因：ok 框架的 `BaseTask.unpause()` 实体是：

  ```python
  def unpause(self):
      self._paused = False
      self.executor.start()   # ← 把整个执行器从暂停里放出来
  ```

  它是给「解除 `task.pause()` 造成的执行器级暂停」用的。
  我们的第二栏**从来没调过 `task.pause()`**，`unpause()` 是纯副作用。
  更糟的是：第一栏【停止】已经释放了截图会话（`capture_method = None`），
  第二栏又把执行器唤醒 → 执行器去取帧但拿不到 → 任务卡住。
- 根因之二：`task.disable(); task.unpause()` 这个写法是**抄框架**
  `TaskCard.stop_clicked()` 的。框架里成立是因为框架的 stop 语义是
  「停掉这张任务卡」；我们第二栏的语义是「暂停自动训练」，
  语义不同，副作用就不同 —— **抄调用序列前先确认语义一样**。
- 修法：`_stop_auto_training` 只留 `task.disable()`。
- 提示词里应该加的那句：**「看到 `xxx.disable(); xxx.unpause()` 这种成对调用，
  先查框架里 `unpause` 的实体：它是不是会动全局状态（这里是 `executor.start()`）？
  如果这个按钮只该管一件事，就别带上那个有全局副作用的一半。」**

### 「任务状态」有滞后：判据要用 `enabled and running`，不是光看 `running`

- 现象：断开游戏后，第二栏还挂着【暂停】好几秒才变【开始】。
- 根因：`task.disable()` 是**同步**生效的（`_enabled` 立刻变 False），

- 提示词里应该加的那句：**「判断『任务还在不在跑』时，
  `enabled`（有没有被停掉）是同步的，`running`（线程有没有退干净）是滞后的。
  要立刻反映状态变化就用 `enabled and running`；只看 `running` 会慢半拍。」**

### 「先置空、后关闭」：连接态要同步断，别把状态变更丢进后台线程

### 扭蛋页：卡面先渲染、价格后渲染，「读不到卡」不等于「页面是空的」

- 现象：2026-11-01 15:09 实跑（周五，扭蛋流）。进步行街 → 看到「超级扭蛋机」动画页 →

- 顺带修了一个**潜在的旧 bug**：`weekend_state()` 只要日期键一变就整个重建 `_weekend`，

### 地图上的标签要连**位置**一起判，不能只认文字

- 现象：地图上步行街的奖励提示写的是「**扭蛋增强**」（平时是「零用钱+」，因为野上
  泷的「扭蛋加成」技能）。这个彩色爆炸标签的含义是「不管钱和队友，直进步行街」，

- 隐患：**判据不看它贴在哪**。队友台词、别的界面的说明文字只要出现同样字眼，
  就会误判成「步行街有加成」→ 不管钱和队友直进步行街 → 走错整天流程。
  （同一类毛病在 `handle_street` 已经栽过一次：地图上的「扭蛋增强」被 `STREET_TITLE`
  的包含匹配判成扭蛋页，见上面那条。）
- 修法（2026-11-01）：连位置一起判 —— `venue_has_street_boost` 要求标签贴在
  **步行街名字的左上方**（Δcx ≤ 0.20、Δcy ≤ 0.12、且在名字左边），
  和 `venue_on_discount`（同一行 + 名字左侧）同一套路。

  地图帧零误报。
- 提示词里应该加的那句：**「界面上某个词出现的次数和位置是有语义的 —— 一个
  '贴着某地点左上角的彩色爆炸标签' 和 '对话里提到的一句话' 是完全不同的东西。
  只按文字匹配全局标签，等于把『有没有这个标记』和『这个标记在不在该在的地方』
  混为一谈。地图上的每个标记（队友气泡 / 打折 / 扭蛋增强）都要带位置判据。」**

### 顶栏专注：`/` 一直被 OCR 读成 `1`，别再指望它认斜杠

### 「白名单」写成 `elif` 就等于给某类对象开了后门

- 现象：2026-11-04 23:56 实跑，精力 23（低于清空阈值 30）时买了**蓝卡**
  「精力转换-体能（消耗所有精力）」，精力被清到 0，当天剩下的训练全废。
  用户当场问「怎么买了一个蓝色的，不是不买吗」——配置里 `扭蛋品质优先` 只有彩/金/紫。
- 根因：`gacha_candidates` 的两条门槛写成了一条 `if/elif` 链：

  ```python
  if c["clear"]:
      if not allow_clear:      # 清空卡：只判精力阈值
          continue
  elif c["quality"] not in base_of:   # ← 白名单只挂在「非清空卡」上
      continue
  ```

  白名单在 `elif` 分支里，于是**清空卡永远不做品质过滤**。清空卡恰好是这类
  流程里最危险的一种（它会把精力清零），漏掉的偏偏是它。
- 修法：两道门槛**各自独立**，白名单在前、阈值门槛在后
  （`src/tasks/training/places/street.py`），并补了回归
  `test_blue_clear_card_never_bought_at_low_stamina`。
- 提示词里应该加的那句：**「凡是『某类对象有额外门槛』，先用反例问一句：
  这类对象是不是**同时也受**通用白名单/黑名单约束？把额外门槛写成 `elif`
  会静默地把它从通用规则里摘出去。判据要写成并列的 `if A: continue`
  `if B: continue`，每一行只否掉一件事。」**

### 「开关拨了不动」先看这个模块的**任务类型**：`TriggerTask` 只在执行器没暂停时才会被调度

- 现象：2026-11-02 用户报「hacking 界面，快速比赛的开关，应该是跟第一栏的启动按钮

  `if self.paused or exclusive_owner: 只跑 job、不调度任务` —— 于是
  `task.enable()` 拨到「开」只是把开关位置位，**执行器不跑就一帧都不动**。

  「快速比赛跟第二栏的开始绑在一起」。

     复位两个开关 + `executor.pause()` + 释放截图）；
  2. 第二栏【开始/暂停】和快速比赛开关：**开**的时候顺手 `executor.start()`
     （`_wake_executor`，只是顺手、不是必须；拉游戏/连设备仍归【启动】），

     反过来**执行器被关掉时，两个模块开关都要复位**（运行基础没了）。

  （`task.enabled` 真不真）；② 这个任务类型会不会被调度（`TriggerTask` 要执行器在跑，
  onetime 任务要入队且执行器在跑）。第二层不满足时，开关要顺手把执行器唤醒

- **不重启的临时通道**：`tools/mcp/training_tick.py` 在 `logs/mcp/hot_reload.json` 存在时，
  会 `importlib.reload` `parsers/scoring/labels/BaseGirlsTask/handlers`，再把新方法
  `setattr` 回**正在用的旧类对象**（TrainingTask 的 MRO 指向旧类）、最后替换
  `TrainingTask.HANDLERS`。这是验收用的旁路，**不是常态**：正式跑请重启 runtime

### handler 是**裸函数**，别在 mixin 类里放 `self.XXX` 常量

- 现象：新 handler 在回归里直接「未命中」，`--all-hits` 也不列它；加 `--verbose` 才看到
  `AttributeError: 'DryRunTask' object has no attribute 'UNMARK_INTERVAL'`。

  在 handler 里根本查不到；而 `parsers` / `scoring` 的类属性能用，是因为 TrainingTask
  真的继承了它们。
- 提示词里应该加的那句：**「handler 的阈值/间隔写成模块级常量；`self.XXX` 只对
  TrainingTask 真继承的 mixin 有效（parsers/scoring/daycycle/places…）。」**
- 顺带：新 handler 记得同时加进 `TrainingTask` 的基类列表，否则单测里
  `task.handle_xxx` 调用不到（运行时靠注册表仍能跑，但测试会漏）。

### 监控页的字段「不更新」：先问「谁在读、在哪些页面读」

- 现象：2026-11-02 用户停在训练日主界面，监控页六维是 982 / 1437 / 1309 / …，
  游戏底栏却是 1079 / 1473 / 1379 / …，一个数都没动；用户原话「有的属性是同步的有的却不是」。
- 根因：`info["attrs"]` **只有一个写入点** —— 训练科目页的 `handle_subject_select`。
  训练日主界面底部摆着同一个面板，却没人读它 → 监控页的六维最多比游戏**晚一整天**；
  而同一页的周/日/专注是 `top_bar()` 每拍写的，所以看起来「有的字段活、有的字段死」。
  另一个放大器：旧写法是**整块替换**，某一帧被说明气泡挡住的那一项会直接掉成「—」。
- 修法（2026-11-03 用户最终口径，两次纠正后的结论）：
  1. `parsers.refresh_attr_info()` **合并**写 `info["attrs"]`（值变了才写日志），
     旧写法是整块替换，某一帧被说明气泡挡住的那一项会直接掉成「—」；
  2. **刷新点 = 进入休息室**：`handle_training_day` 的决策拍调 `parsers.snapshot_lounge()`，
     **六维 + 精力 + 零用钱**三项一起拍，`_lounge_snapshot_done` 保证每次进这页只拍一次
     （离开时由 `LEAVE_RESETS` 清掉）。科目页**不再**承担刷新，只消费 `info["attrs"]` 做排行的兜底；
  3. 不在主循环「每拍读」：校门口 / 地图没有六维面板，周末加的是零碎属性
     （属性+10、精力+…），回头累加既对不上面板也没意义 —— **只在该拍的地方拍一次**；
  4. 顺手补上零用钱（`parsers.read_money()`，周末商店/游戏厅本来就在用同一份取法，
     `top_bar` 里写进 `info`），之前 `coin` 只有 `None` 占位，监控页永远是「—」。
- 验证口径（别靠猜）：`tools/win_shot.py <pid> out.jpg` 把 GUI 和游戏各截一张，逐格对数字；
  再 `tools/ocr_dump.py` 抓帧 OCR 跑一遍 `read_attribute_values` / `top_bar`，看读出的数是不是
  游戏上那几个（这次读出 5 个六维 + 精力 118/130 + 零用钱 75：体能被鼠标悬停气泡
  「提高看破对手意图…」盖住了 → 正好检验合并语义）。
- 提示词里应该加的那句：**「界面上的数字『不更新』，先别怀疑刷新链路，先问三件事：
  ① 这个字段谁在读、在哪几个页面读（只在一个页面读 = 其它页面全是过期快照）；
  ② 任务当时在不在跑（OCR 数据没有拍就没有，任务停着时所有字段都不该动）；
  ③ 这块数据该在哪个界面拍 —— 只在**它真正完整可见**的那个页面拍一次，
  别每拍乱读，也别在只能看到零碎增量的页面上反推总数。
  写 `info` 里的快照一律『合并』而不是整块替换，遮挡/漏读时才不会掉成「—」。」**

### 炒股选股「队友多的优先」：数气泡数不出人数，要数**头像**

- 现象：2026-11-02 用户实拍（`logs/debug/1102-234130_stock03.jpg`）：左边卡头顶 1 个队友、
  右边卡 2 个；老规则（气泡数 → 价格取高）没有这条口径，选谁全看价格。
- 根因：**气泡一张卡最多一句**（「就选它了！」「一定能赚！」），2 个队友也只冒一句 ——
  用气泡数「有几个队友」永远只能得到 0/1。用户当场给的判据是「默认选队友多的」。
- 修法：`parsers.stock_teammate_counts` 数**张开的嘴**：chibi 头像的嘴是同一块颜色
  （BGR≈160/172/238，`r-g>58`）、大小 14~16x7~8、横窄条；皮肤 `r-g≈44`、脸 30x25、
  头发块 38x40 全被宽高比/尺寸过滤挡掉。每张嘴按 x 归给横向最近的那张卡。
  头像一个都认不出来时**退回气泡判据**，不让规则彻底失效。
- 顺带修掉的识别漏洞：三张卡的类型名**会重复**（`风险型/风险型/稳健型`），
  老写法「每个类型名各取一个框」会漏掉中间那张 → 改成按 x 收集 + 同列去重。
- 提示词里应该加的那句：**「『有几个 X』这种量，先确认界面上哪个元素是**一 X 一个**：
  气泡/台词是『一格一句』，不是『一人一句』；要数人头就找人头本身的固定特征
  （这次是同一套 chibi 表情的嘴色），并用宽高比 + 尺寸把脸/头发/描边排除掉。」**

### 餐厅「队友多两个才改选」：胶囊只能分「有/没有」，人数要数**脸**

- 现象：2026-11-03 用户口径「桌游GM 的队友比当服务员多两个 → 优先桌游GM」。
  旧判据 `mates_on_card` 的深蓝兜底只能给 0 或 1：实测帧
  `docs/shots/restaurant_cards.png` 左卡 2 人、右卡 1 人，两张都读成 1 → 永远平局，
  用户这条规则不可能生效。
- 修法：`parsers.mate_face_count` 数**脸**。同一套 chibi 的脸是同一块很亮的暖肤色
  （r≥232、g≥205、b≥190、r−b≥20）；连通块面积 0.0002~0.0016 屏面积、宽高比 0.55~1.5。
  两个头之间隔着头发，不会粘成一块（灰度/蓝发/金发都比肤色暗，被阈值挡掉）。
  搜索范围：标题上方 6 个字高、横向 ±1.1 个字宽 —— 够装两个头，也碰不到隔壁卡。
  数不到（=0）时退回旧的「有/没有」，规则不会彻底失效。
- 提示词里应该加的那句：**「要『数出个数』，先找『一个 X 一块』的像素特征；
  只输出有/没有的判据永远回答不了『多几个』。定阈值别拍脑袋：拿真帧把每个候选连通块的
  面积/宽高比打出来，看目标和非目标差几倍。」**

### 餐厅「多两个才改选」还是不生效：兜底判据会给「没有队友」的那张卡白送 1 个

- 现象：2026-11-03 20:37 实跑（`logs/events/1103-203745_handle_restaurant.jpg`），
  左卡头顶明明 2 个 chibi、右卡一个都没有，日志却是
  `当服务员=1人、桌游GM=2人｜…｜桌游GM 只多 1 人，不够 2 人 → 当服务员`。
  同一个 run 的 15 次餐厅决策里**当服务员恒为 1 人**（也有 2 人、0 人的抖动），
  规则一次都没触发过。
- 根因：不是数脸坏了（四帧复算 2/0、1/0、2/0 全对），是**「数不到就退回深蓝兜底」**
  这条兜底把「卡片自己的图标」数成了队友：现版本桌游GM 的骑士、当服务员的背心
  都是深蓝的，正好落在兜底那条带（标题上方 2.4~4.6 个字高）里 ——
  背心深蓝占比 0.107 > 0.08 阈值 → 白送 1 个；骑士 0.075 刚好没过线（所以只有一张卡脏，
  差 1 个而不是差 0 个，最难看出来）。跟 `quality_cards` 里「卡头图标被数成队友」同一个坑。
- 修法：`RestaurantPlace.card_mate_counts` 改成**先数脸；只要两张卡里有一张数到脸，
  就只认脸**，一张脸都没有（= 旧版深蓝圆标记的界面）才退回兜底。日志里带
  `（队友按数脸/深蓝兜底）`，下次一眼能看出走的哪条。
  复算真帧：`[2,0] 数脸 → 桌游GM`（修前是 `[2,1] → 当服务员`）。
- 提示词里应该加的那句：**「保留兜底判据可以，但要给它加一道『主判据失效』的闸门 ——
  主判据**至少在一处**取到值时，兜底就不许再参与，否则兜底会把它自己的假阳性加到
  真实读数上（这次是 2 人 vs 0 人 → 2 人 vs 1 人，差 1 个，刚好跨不过阈值）。
  另外：别把「卡片自己的图标」当成「卡片上的徽标」，图标和徽标同色时只能靠位置/结构区分。」
  排查顺序也记一下：**先看日志里的人数是不是恒定值**（恒为 1 = 兜底在打分），
  再去查数脸 —— 恒定值几乎一定是某个「有/没有」判据在冒充计数。**

### 倍速自己变成 OFF：先确认「这条横带里图标在不在」，再谈「有没有空心三角」

- 现象：2026-11-02 23:41:34，脚本在炒股事件结束后回到训练日主界面，**第一拍**就点了
  倍速图标一下 —— 正在跑的 3x 被点成 OFF，接着又补 3 下才回到 3x（用户当场看到）。
- 根因：`topbar.speed_at_max` 只看「空心三角占比 ≥ 0.05 = 没到顶」。
  页面刚回来那一拍倍速图标还没画出来，这条横带里是**别的东西**：
  实心 0.00 / 空心 1.00 → 判成「还有空心三角」→ 点一下。
  （炒股页自己的金币徽章就压在倍速图标的坐标旁边，`第5周股票走势` 这种文字也命中 `WEEK_RE`。）
- 修法两条一起上：
  1. **先确认图标在**：实心占比 < `SPEED_SOLID_MIN`(0.10) → 返回 None，调用方不点。
     逐档实测最低的真档位是 1x 的 0.26，留了一倍余量；没有图标时是 0.00。
  2. **页面第一拍不碰倍速**：`handle_training_day` 里 `ensure_speed` 挪到淡入拍之后
     （和「出行」按钮、加强训练卡片同一个 `HUB_SETTLE_TICKS` 约定）。
  另外像素判读改用**本拍识别的那一帧**（`_tick_frame`），不再读 `self.frame`（那是采集线程
  的最新画面，可能已经翻页/淡入到一半，和 `texts` 描述的不是同一屏）。
- 提示词里应该加的那句：**「像素判据都是『条件 A → 结论 B』，先问一句『A 的前提成立吗』：
  这次的前提是『这条横带里真的画着倍速图标』。用占比类判据时，样本里一定要同时包含
  『目标不在』的那一类，否则判据会把『什么都没有』读成某个具体状态；页面的第一拍
  （淡入）默认不可信 —— 决策和像素判读都要等一拍。」**

### 两个量纲不同的收益不能加进同一个分数：分差会盖住用户要求的档位

- 现象（2026-11-03 10:11，第2周星期五，54/130、398 币）：扭蛋三选一，右卡「意识增加+」
  **卡头有队友标记**、中间是「精力恢复+」，脚本买了中间那张。用户：「应该优先选有队友的」。
- 根因：恢复量按 `min(恢复, 上限−当前) × 0.5` **直接加进了 score**（+38），
  而「队友」只是分数完全相同时的 tie-break → 38 分的分差让队友永远轮不到。
  **识别全对**，错的是把「精力」和「品质/队友」放进了同一把尺子。
- 同源的另外两处（同批修掉）：
  1. 事件选项/加强训练：精力 × 0.2 折成属性点混进 ev —— 「属性+3，精力+30」= 9 分，
     压过「属性+8」= 8 分；满精力时也照算。
  2. 技能三选一：`gem*100 + quality*10 + has_pref`，而 gem 只是「左上角金橙像素占比
     > 0.03」的猜测 → 白卡带道具(110) 压过彩卡(30)。
- 修法：**显式档位**代替加权和。
  扭蛋：品质 → 增强款 → 队友 → 恢复价值 → 价格；
  事件：属性 ev → 能用上的精力（按余量封顶）→ 靠右；
  技能：品质 → 道具 → 标签。
  恢复量/精力仍然参与，但只作为**次级比较**，且必须按余量封顶（满精力 = 0）。
- 提示词里应该加的那句：**「打分函数里每加一个『收益换算成分数』的项，先问这句：
  它和原来的第一档是不是同一个量纲？能不能靠它把用户明确要求的档位（品质/队友）
  翻过去？凡是量纲不同（精力 vs 属性、像素占比 vs 品质），只能做『打平后的下一档』，
  不能加进同一个数。」**

### 辅助函数里的裸名字漏导入：异常被 debug 吞掉 = 这个功能从来没跑过

- 现象（2026-11-03 19:15 实跑）：`handlers/match.py: dump_skill_frame` 每局最多存 6 张
  技能三选一帧，用来校准「有队友/有道具」判据 —— 实际上**一次都没成功**。
  `run.log` 里只有 4 条 `DEBUG 技能帧存证失败: NameError: name 'PROJECT_ROOT' is not defined`。
- 根因：`match.py` 只 `from ...constants import JPEG_PARAMS`，`PROJECT_ROOT` 从没导入；
  外面套着 `except Exception: log_debug(...)`，失败就一行 DEBUG，跑完没人会翻。
- 判据：**「功能没生效」先查「有没有被静默吞掉的异常」** —— 日志里 `DEBUG` 级别的
  `失败: XxxError` 一律当红旗。回归里已有这道门禁：`check_handlers.py: check_undefined_names()`
  （AST 扫「裸名字用了但没导入/没定义」，2026-11-03 全项目只此一处，修完 0 处）。
- 提示词里应该加的那句：**「`try/except` 把异常降成 debug 等于把 bug 藏起来。凡是
  『本该产出文件/数据』的功能，日志里必须有成功计数：只有失败告警、没有成功行，
  就是没跑过。」**

### 顶栏精力：同一格数字有两种坏法，护栏要比坏法更严

- A. 图标并进数字框（斜杠还在）：`3 54/130`、`3130/130` → 当前值 > 上限就是图标；
- B. **斜杠被吃成 `1`**（2026-11-03 19:15 实跑）：`3921130`(=3 92/130)、`521130`(=52/130)。
  这条**不一定带图标**，光看文本分不清 `3`+`0/130` 和 `30/130`。
- 护栏（宁可不洗，也不改坏）：上限必须落在 `100..250`（精力上限实测 115~164，
  挡掉 `/70`、`/9`、`/1550` 这类别的进度条和价格）；没图标又只剩一位前缀
  （`11228` 是零用钱还是 `1/228`？）不动；同一帧里已有读对的 `/130` 就只认它。
- 验证方法：把历史日志里**所有 OCR 文本**回扫一遍（336 万条），改动必须全部落在
  精力上限那一档上 —— 只看「样本里对不对」永远发现不了 `1001/9 → 001/9` 这种误伤。

### 卡住判据要数「同一天攒了多少」，别数「秒」

- 现象：脚本在休息室/校门口反复点同一个按钮，一百多下都没推进，看门狗一次也不响。
- 根因：老判据是「N 秒没有任何点击 + 界面指纹没变」。① 顶栏数字/星标每拍都在闪，
  指纹每拍都变 → 条件永远不成立；② 反过来「等动画」也满足「没点击」，会误伤。
- 用户口径（2026-11-04 两版）：**按「同一天」数** —— ① 休息室/校门口点超过
  `卡住点击上限`（100）下；② **所有页面**（含看不到日期的）过了 `单日最大操作数`（100）拍，
  日期还没更新。超过就干预：存证 + 清掉当天拦路标记 + 点屏幕中央继续；
  **读到新日期才归零**（看不到日期的帧照常计数、不动日期键）；同一天干预 3 次还推不动才停。
- 阈值不是拍脑袋：从历史日志量「换天间隔」= 中位 16 拍 / p90 44 / 最大 106，
  所以 100 既不误伤正常的一天，又能在真卡住时一分钟内动手。
- 唯一的豁免是**声明表**（`handlers/__init__.py: DAY_BUDGET_EXEMPT`：注册球员 542 拍 /
  比赛快进 / 赛前准备），不是「这一帧没日期就不数」—— 后者会留一个「切到无日期页面
  就绕过限制」的漏子。
- 提示词里应该加的那句：**「卡住判据先问『这个页面正常推进时长什么样』—— 有连点
  正常推进的页面（剧情/科目/地图）要用『按天攒』而不是『按秒』；要豁免就写声明表
  （谁长跑谁声明），别用『看不到日期就不计数』当豁免 —— 那等于给空转留后门；
  阈值拿历史日志的间隔分布来定。」**
