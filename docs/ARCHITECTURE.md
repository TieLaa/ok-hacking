# 架构：分层与模块边界

> 2026-11-01 用户定稿。这份文件是**模块边界的唯一事实来源**；
> 改代码前先看 `docs/ENGINEERING.md`（目录职责）和本文件末尾的「落地顺序」。

## 一、总原则

**每个脚本只负责自己的部分。** 判断归业务模块，通用能力归基础设施。

三条推导出来的规则：

1. **一天的标识只有一个：顶栏的「第N周 星期X」。**
   游戏里「打工 / 消费 / 划船 / 买扭蛋」只要发生交互就过一天，
   所以**日期变了就是新的一天，没变就是同一天**。
   不需要各模块自己维护「今天过没过」——那正是 bug 的来源。
2. **新一天有两个入口，它们是同级的**：
   ① 训练日主界面（右下「训练 / 休息」）
   ② 出行前跟队长说话的界面（「出行」按钮所在的那页）
   它们的判断放**同一个模块**，全局日期也写在那里。
3. **系统级 UI 与事件级 UI 分开**：
   固定位置固定逻辑的（返回 / 倍速 / 历史记录 / 菜单 / 快进 / 自动·手动）
   归系统层；具体的界面事件归各自的业务模块。

## 二、层次

```
src/tasks/training/
├─ flow.py          单拍状态机、卡死检测、存证        （不含业务判断）
├─ parsers.py       只读解析：OCR 文本 → 结构化数据   （不点击）
├─ scoring.py       纯打分
├─ daycycle.py    ★ 全局日期 + 两个新一天入口 + 当天状态
├─ systemui.py    ★ 系统级 UI（固定位置固定逻辑）
├─ handlers/        按界面域分的 handler（认界面 → 调模块 → 点）
├─ ui/
│  ├─ labels.py     界面**文字**（按钮表、页面标记、正则）
│  └─ Defs.py       界面**几何**（区域、坐标、ROI）
└─ constants.py     模块级常量（风格表、周末计划表等）
```

★ = 2026-11-01 新增。

## 三、模块边界

### 3.1 `daycycle.py` —— 全局日期 + 一天的周期

**唯一**读顶栏日期的地方。其他模块不自己读，向这里要。

| 接口 | 作用 |
|---|---|
| `current_day(texts)` | 返回 `(week, day)`；**每帧只读一次**并缓存 |
| `day_name()` / `is_weekend()` | 星期几 / 是不是周末 |
| `day_state()` | 当天状态（`visited` / `gacha_spent` / `outing_done` …） |
| `training_day_action(texts)` | **入口①**：今天练还是休 → `("训练"/"休息", 理由)` |
| `outing_offer(texts)` | **入口②**：这一页要不要外出 → `("点按钮"/"推进对话", 理由)` |
| `resolve_style_by_config()` | **路径 A**：配置里的队长 → 查表定流派 |
| `resolve_style_by_calendar_name(name)` | **路径 B**：日历上的队长 → 查表定流派 |
| `_resolve_style_step(texts)` | 路径 B 的多拍状态机（返回→点日历→抓名字） |
| `captain_alert()` | 认不出队长 → **弹窗「未能识别到队长」**，不许保底 |

**为什么必须收口**（真实 bug，2026-11-01）：

`top_bar()` 会被 20 多处调用，同一帧里各读一次可能读到不同的值
（OCR 抖动）。`day_state()` 原来按「日期键变了就重建整个状态」，
于是顶栏抖一帧（扭蛋页只读到专注、没读到「第1周 星期五」）
→ `visited` / `gacha_spent` 全被清空
→ 当天「已经买过扭蛋」的事实丢了，又要去餐厅打工一次。

现在：读不到**完整**日期键（周或星期缺一）→ 沿用旧状态。

**门禁**：`check_handlers.py: check_date_entry()` ——
handlers 里直接 `top_bar()` 取日期就报红。

### 3.1b 队长 / 流派：两条路径，**都不许保底**

用户 2026-11-01 口径：

```
路径 A（配置里填了队长）
    查 STYLE_BY_NAME → 找到 √（定流派）
                    → 找不到 → 弹窗「未能识别到队长」

路径 B（配置为空 = 快速接手）
    点返回 → 直到回到「带日历的页面」（训练室 / 校门口）
          → 点日历 → 抓队长名字 → 查表
          → 认到 √（定流派）
          → 认不到 → 弹窗「未能识别到队长」
```

**为什么必须是「主动返回 + 点日历」，不能等**：

- `handle_style_probe`（旧机制）要求这一页同时有「星期」+「休息」 ——
  那是**训练室**专属。**校门口没有「休息」** → 接手的局在周末永远点不了日历
  （2026-11-01 实测：周末地图上 `handle_style_probe` 返回 False）。
- 日历页**自己不带日期**（实测 111 帧里只有 3 帧带）→
  必须先回到训练室/校门口（顶栏有「第N周 星期X」）才有日期。

**「带日历的页面」怎么认**：不靠文字，靠行为 ——
有日期、且**不是**地点内页/地图（那些也带日期，但左上角不是日历）。

**旧的 `handle_style_probe` 已删除** —— 它和新机制是同一件事的两个实现，
留着会互相干扰（一个在训练日点日历，一个主动返回）。

**日历位置是系统级的**：`SystemUIHandlers.CALENDAR_POINT = (0.035, 0.06)`
（训练室和校门口左上角是同一个按钮）。

### 3.2 `systemui.py` —— 系统级 UI

固定位置、固定逻辑、跟业务无关的控件：

| 控件 | 位置 | 归属 |
|---|---|---|
| 顶栏 倍速 | `(0.760, 0.044)` | `ensure_speed()`（判读在 `ui/topbar.py`） |
| 顶栏 历史记录 | `(0.819, 0.045)` | 只读，安全 |
| 顶栏 菜单 | `(0.875, 0.052)` | **禁止点击**（误触毁局） |
| 顶栏 返回 | `(0.939, 0.043)` | `click_back()` |
| 比赛内 ▶▶ 快进 | `(0.062, 0.928)` | `click_match_fast_forward()` |
| 比赛内 自动/手动 | 左下角 HUD 区 | `handlers/match.py`（有业务含义） |

**这一层不做业务判断**（今天练不练、去哪个地点），只管「按这个固定控件」。

### 3.3 事件级 —— 各业务模块

每个地点/事件有自己的模块，只管自己的判断：

```
places/
├─ map.py         ★ 决策层：今天去哪几个地点、先去哪个（**唯一知道所有地点的**）
├─ street.py        步行街（扭蛋）
├─ restaurant.py    餐厅（打工）
├─ park.py          公园（散步/划船/野餐）
├─ arcade.py        游戏厅（小游戏）
└─ shop.py          商店（买器材）
```

**地图模块是决策层**：它比较各地点「今天值不值得去」，然后点地点名。
地点模块**不需要**互相知道 —— 「现在在餐厅但今天本来该进步行街」
这个问题的答案由地图模块给出（说明是钱不够或没有合适的扭蛋）。

**地图模块 vs 地点模块的接口**：

```python
class MapPlace:
    def weekend_map_page(self, texts)          -> bool  # 这是不是地图？
    def today_places(self, day, st)           -> list  # 今天去哪几个（有序）
    def prefer_venue(texts, places, day)      -> list  # 先去哪个

class StreetPlace:      # 其余四个地点同形
    def xxx_page(self, texts)                -> bool  # 这是不是我的页面？
    def <做什么>(...)                        -> ...   # 纯判断
    def <状态>                              -> ...   # 我自己的状态
```

**拆分粒度**：不要按「界面」拆，要按**业务**拆。
界面上「步行街内页」和「地图上步行街那个按钮」是同一家事的两个阶段。

### 3.4 状态归属

| 状态 | 归谁 | 为什么 |
|---|---|---|
| `visited` | 地图模块 | 它决定「今天该去哪、别再进哪个」 |
| `gacha_spent` / `gacha_tried` | 步行街模块 | 只有它知道「买没买成」 |
| `park_choice` | 公园模块 | 只有它知道「今天选了什么」 |
| `outing_done` | `daycycle` | 跨入口（训练日/周末首页） |

**因为交互就过天，所以这些状态按日期键重置就够了** ——
「只要日期没变就不会改变 visited」。

## 四、门禁

`tools/check_handlers.py` 现有四道：

| 门禁 | 管什么 |
|---|---|
| `check_architecture()` | 判断分支里不许出现 handler 名字（依赖进 `handlers/__init__.py` 的声明表） |
| `check_labels()` | 调用处不许写按钮文案（要走 `labels.BUTTONS`） |
| `check_date_entry()` | handlers 里不许直接读日期（唯一入口 = `daycycle.py`） |
| `check_places()` | 地点模块之间不许互相知道（该由地图模块决定去哪个） |
| `check_interactions()` | 通用交互层不许出现地点名（坐标/正则由调用方传进来） |
| `check_config()` | 配置默认值只许写在 `config_spec.py`；读的键必须在 spec 里声明 |
| `check_mojibake()` | 源码里不许出现 U+FFFD（被 GBK 吃掉的字符） |
| `check_undefined_names()` | 裸名字用了但没导入/没定义（漏 import 的模块级常量；被 try/except 压成 DEBUG 的那类 bug） |
| 回归图 | `docs/shots/expected.json` 锁「哪张图命中哪个 handler」 |

### 3.6 `config_spec.py` —— 配置项的**唯一声明**

每个配置项在**一处**声明：键名 / 默认值 / 类型 / GUI 控件 / 说明。

```python
Spec("扭蛋清空精力阈值", 30, INT, "精力低于这个值才买「消耗/清空所有精力」的扭蛋…")
```

`TrainingTask.default_config` / `config_type` / `config_description`
都从它生成 → **默认值只有一处**。

**为什么必须收口**（2026-11-01 实测的三个问题）：

1. **默认值写在两处**。`default_config` 声明了 40，调用处又写一遍
   `self.config.get("休息精力阈值", 40)` —— 那个 40 **永远不生效**
   （config 一定命中 default_config）。实测 24 处调用点全是这种死代码。
2. **有配置项用户在 GUI 里配不到**。`扭蛋清空精力阈值`（weekend.py 读了）
   和 `技能按键`（当时由模板演示任务读了，任务已下线）没在 `default_config` 声明 → GUI 上没有。
3. **有配置项声明了但没人读**。`扭蛋优先属性`（10-26 选卡重写后就没读取点了，
   但说明还写着「会消耗所有精力」—— 与现行规则**相反**）。

**去掉调用处默认值的连带影响**（踩过的坑）：

`config.get(key)` 在键不存在时返回 **None**（falsy），
所以「允许进步行街」会被当成 False。生产环境不会缺键
（`ok.util.config` 用 `default_config` 补全），但**测试夹具**原来只有 1 个键
→ 25 条测试挂掉。修法：夹具改成用**真实的 default_config**（和生产一样）。

**门禁**：`check_handlers.py: check_config()` ——
调用处不许写默认值、读的键必须在 spec 里声明、声明了没人读的报出来。

**顺带清掉的 3 个死配置项**（都是 10 月就存在的）：

| 键 | 为什么是死的 |
|---|---|
| `扭蛋优先属性` | 10-26 选卡策略重写后就没读取点了；说明还写着「会消耗所有精力」，与现行规则**相反** |
| `只在决战前清空` | 声明了没人读（决赛判据还没实测） |
| `快进重复间隔(秒)` | 声明了没人读（小游戏改成自动打完，不再需要手动补点） |

现在 **25 项声明 / 25 项被读** —— 门禁 0 警告。

第 3 步的样板：步行街（它今天暴露的问题最多）。
判据和状态搬到 `places/street.py`，`handle_street` 退化成
「认页面 → 调模块 → 点」。

**地点模块的接口形状**（`places/street.py`）：

```python
class StreetPlace:
    def street_page(self, texts)          -> bool   # 这是不是我的页面？
    def street_enabled(self)               -> bool   # 配置开关
    def gacha_candidates(cards, ...)       -> (best, detail, all)  # 买哪张（纯判断）
    def has_boost_label(texts, box)        -> bool   # 地图上「扭蛋增强！」标签
    def street_state(self)                 -> dict   # 我自己的状态
    def mark_tried() / mark_spent()       -> None
```

模块**只给判断，不点击** —— 点击由 handler 做。
这样模块可以被离线测试（不需要帧、不需要点击）。

### 3.5 `interactions.py` —— 通用交互层

跨地点复用的**动作**，**零地点知识**（2026-11-01 第 4 步）：

| 接口 | 作用 |
|---|---|
| `choose_option(texts, names, ...)` | 选一个选项 + 按确定 |
| `confirm_after_choice(confirm_region=...)` | 按「确定」（**区域限定**） |
| `exit_with_coords(coords, ...)` | 按**给定**坐标退出（坐标由调用方给） |
| `buy_stalled(scene, money, item, counter=...)` | 购买有没有成交（计数器由调用方持有） |
| `find_go_button(texts, pattern)` | 按**调用方给的正则**找「前往XXX」 |

**为什么必须零地点知识**（2026-11-01 的 5 个具体问题）：

1. `choose_option` 的「确定」原来**全屏找** → 正文里的「确定」会被点
   （`labels.py` 记过两次同类事故）。现在**区域限定**。
   *实测确认安全*：扫全部真实存证帧 —— 公园/餐厅的 112 帧根本没有「确定」按钮；
   有「确定」的 `handle_street`/`handle_boost_training`/`handle_arcade`
   全部在 `confirm_bar` 里；在区域外的只有 `handle_skill_select` 和
   `handle_rest_confirm`，但它们**不走 `choose_option`**。
2. `leave_street` 的兜底坐标是扭蛋页专属的 → 现在归**步行街模块**
   （`StreetPlace.EXIT_COORDS`）。
3. `buy_stalled` 的计数是共享变量，商店/游戏厅互相清对方的状态
   → 现在**每个场景一份**（`buy_counter(scene)`）。
4. `ACTIVITY_GO` 一个正则塞了 9 个地点 → 现在每个地点模块给自己的正则
   （`places/activities.py`）。
5. 三个退出方法各写各的兜底坐标 → 通用层收成 `exit_with_coords`。

**门禁**：`check_handlers.py: check_interactions()` ——
通用层的**代码**里不许出现地点名（docstring 里说明「为什么」不算）。

## 六、被否掉的方案

| 方案 | 理由 |
|---|---|
| 「今天上下文」对象（TodayContext） | 游戏里交互就过天，日期**就是**全局状态，不需要组装快照 |
| 各模块自己读顶栏 | 同帧各读一次会读到不同值 → 状态被误清（2026-11-01 的真实 bug） |
| 独立决策层（超出地图模块） | 地图模块本来就是决策层，不新增层 |
| 状态机 / 配额模型 | `reports/REVAMP_PLAN.md` 已否；主循环「一拍一个动作」的心智模型更稳 |
| 按界面拆模块 | 「地图上的步行街按钮」和「步行街内页」是同一家事，按界面拆会把它们分开 |
