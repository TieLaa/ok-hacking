## 术语：专注 / 精力（2026-11-02 规范用词）

顶栏只有**一个数字**，按界面语境叫两个名字，别再混用「体力」：

| 名字 | 语境 | 含义 | 实现 |
|---|---|---|---|
| **专注** | 大厅 | 每日限量的资源。开训练要扣它；不够时游戏弹「训练所需专注还差 25，是否进行回复呢？」 | `top_bar()` 的 `stamina`、`flow.rest_threshold` |
| **精力** | 训练内 | 随活动变动的资源：训练科目、打工、公园野餐、扭蛋「清空/消耗所有精力」 | 同一个数字，但判据与日志用「精力」：`休息精力阈值`、`扭蛋清空精力阈值`、`WORK_STAMINA_COST` |

- 游戏原文只出现过「专注」（大厅开训练，`logs/debug/1027-192726_nochange3/ocr.txt`）和
  「精力」（训练结算「精力降低了X」、休息确认「可恢复精力」、扭蛋「消耗所有精力」），
  **没有「体力」**。OCR 判据里保留的「恢复体力 / 体力不足」只是旧文案别名，不是术语。
- 配置项跟着改名：`休息精力阈值`、`扭蛋清空精力阈值`。旧配置里的「体力 / 专注」键由
  `config_spec.migrate_saved_config()` 在 `load_config()` 之前搬过去，值不丢。
- 2026-11-02 之前的日志与 `docs/RUN_REPORT_*` 里写的是「体力」，读老记录时按上表换算
  （大厅语境 → 专注，训练语境 → 精力）。

## 0. 流派：只由队长决定（2026-10-29）

实现：`flow.style` / `flow.reset_style` / `flow.resolve_style` / `handle_style_probe` /
`handle_training_plan` / `parsers.style_for_name`

**流派不是配置项，是队长的属性。** 本任务只负责「快速接手」这一条：

| 流程 | 怎么定流派 |
|---|---|
| 快速接手（本任务） | 流派为空 → 进训练后在训练日主界面点一次左上角打开日历 → 读「XX的训练计划」→ 查表写入 |
| 全自动（另一条流程，尚未实装） | 它自己把流派写进 `_style`（`run()` 之前），本任务看到有值就不再点日历 |

| 时机 | 行为 |
|---|---|
| `run()` 开始 | `resolve_style()`：配置里有队长 → 查表定流派；配置为空 → 清空流派等日历 |
| 点「开始训练」 | `reset_style()` 清空流派（新的一局，队长可能换了），选中的队长匹配配置则再套用配置流派 |
| 训练日主界面 + 流派为空 | `handle_style_probe` 点左上角 (0.035w, 0.06h) 开日历，最多 3 次、3 秒冷却 |
| 日历页 | `read_plan_captain` 取左上角名字（只显示姓氏，按前缀查表）→ 写入 `_style` → 点右上角关掉 |
| 查表查不到 | 按「训练流」跑并告警，不再反复开日历（SR/R 卡还没收录） |
| 还没定下来之前 | `style` 一律返回「训练流」（最保守） |

- **队长的唯一来源是监控页的「指定队长」勾选框**（2026-11-01）。
  配置里有队长就按它定流派，**不管这一局是不是从大厅开的**。
  - 旧逻辑只在 `is_lobby()` 时套用配置队长，理由是「接手别人的局时实际队长可能不是
    配置里那个」。但**日历只在训练日弹**：接手的局如果当前是周末（非训练日），
    就永远读不到实际队长 → `_style` 一直空着 → `style` 兜底成「训练流」→
    **扭蛋流跑成训练流**（2026-11-01 19:19 实跑日志：
    `非大厅开局 → 流派以游戏内队长/日历为准` + `流派：训练流（待日历识别队长）`）。
  - 现在由 `flow.resolve_style()` 统一决定：配置里有队长 → 查表定流派（查不到才回落到日历）；
    配置为空（无队长模式）→ 清空流派，等日历认实际队长。
- 角色表 `STYLE_BY_NAME` 抄自 `docs/roster/ssr_roster.json` 的 `style_tag`（18 个 SSR）。
- **名字比较一律过 `Defs.norm_name` / `Defs.name_matches`**（2026-10-31）：游戏里读到的名字
  和表里的写法不一样 —— 实测 `SR-亚理纱贾斯敏` vs 表里 `亚理纱·贾斯敏`（间隔点被 OCR 吃掉、
  底部名字行还带稀有度）。旧判据 `want in name` 直接比字符串，16 张队长卡全被当成「不是她」，
  最后报「队长池里没有」并停任务（`logs/mcp/sento_summary.txt`）。同一套归一化也用在
  `style_for_name` / 监控页下拉回填 / `_style_from_config`。
- 日历页有专属 handler，**必须排在所有地点 handler 之前**：这一页带「野餐/划船/转动扭蛋」，
  旧版被 `handle_street` 抢走（2026-10-27 00:54 误当扭蛋页退出 + 误记「步行街已去」）。

## 0.5 无队长模式：不接开局（2026-10-31）

实现：`flow.no_captain_mode` / `flow.stop_for_no_captain` / `handle_lobby`、`handle_training_entry`、
`handle_captain`、`handle_team`、`handle_note_select`、`handle_equipment`、`handle_confirm_team` 的闸门

**`指定队长` 留空 = 无队长模式**（配置项 `无队长不接开局` 默认开）：

| 场景 | 行为 |
|---|---|
| 当前在训练日主界面 / 科目页 / 比赛等**已有局** | 照常跑，和以前一样 |
| 遇到大厅 / 训练剧本 / 训练核心（选队长）/ 选择队友 / 选择笔记 / 选择器材 / 确认编队 | **不点任何东西**，记一条告警后停止任务 |

理由（用户 2026-10-31）：这些页面不点就进不去训练，没法真的「跳过」；
所以无队长时不替你开局，只跑你手动开好的局，一局结束回到大厅就停。

- 监控页的「指定队长」勾选框就是切换这个模式：取消勾选 → 清空 `指定队长`
  **并清掉运行期的流派**（`task._style`）。
  勾选框**默认不勾**（2026-11-01）：旧版默认勾上，而下拉第 0 项是「── 训练流 ──」
  分组标题 —— 用户一进页面就等于「指定了第一个训练流角色」，扭蛋流被写成训练流。
  勾选时用下拉**当前**选中的角色，不是「列表第一个」。
- 回归桩（`tools/check_handlers.py`）把 `无队长不接开局` 设成 `False`，保持旧的自动选人流程可测。

## 1. 出行地点：出门门槛只看零用钱（2026-11-10）

实现：`places/map.py: today_places / prefer_venue`（`flow.weekend_priority` 是它的旧名）、
`constants.WEEKEND_PLAN` / `WEEKEND_MAIN_PLACE` / `WEEKEND_WORK_MONEY_GATE`、
`handle_weekend` / `handle_go_out`

| 星期 | 流派 | 去哪（顺序 = 优先级，前一个走完再下一个） |
|---|---|---|
| **任何出行日**（含周五额外周末） | **训练流** | **按精力缺口**：缺口 ≥ 30 → 公园（≥70 野餐，否则划船）；缺口 < 30 → 餐厅打工（2026-11-11） |
| 周六 | 商店流 | 餐厅（打工） |
| 周日 | 商店流 | 餐厅（打工） |
| **任何出行日**（含训练日的额外出行） | 扭蛋流 / 小游戏流 | 主地点 / 餐厅二选一，只看零用钱门槛 |

### 扭蛋流 / 小游戏流：钱够就去主地点（2026-11-10 用户口径）

主地点：扭蛋流=步行街、小游戏流=游戏厅（`constants.WEEKEND_MAIN_PLACE`）。

| # | 条件 | 去哪 |
|---|---|---|
| 0 | 零用钱读不到 | 主地点（不拿打工赌今天的消费） |
| 1 | 零用钱 < **360**（`WEEKEND_WORK_MONEY_GATE`） | 只去餐厅打工 |
| 2 | 零用钱 ≥ **360** | 主地点 |

- **不分星期**：训练日的额外出行（一星野上泷的周五、二星的第 9/16/30 天）走同一条
  门槛，所以 `today_places` 对这两条流派的候选固定是「主地点 + 餐厅」。
- **队友气泡不参与**（2026-11-10）：气泡看不到品质（带队友的可能是根本不买的蓝卡），
  也看不到刷新后的批次（买一颗刷一批）。买卡时队友只在同品质之间当 tie-break
  （`places/street.py`），所以地图气泡对「去不去」没有预测力，只当添头。
- **标签不豁免钱门槛**：「扭蛋增强！」/ 打折都不改变这个判断。`street.has_boost_label`
  判据本身保留（位置判据仍有测试），但不再接到地点决策上。
- 为什么是 **360**：一次步行街不是买一颗就结束 —— 羽濑川「再买一个」首次必触发、
  之后 57%（7 级 60%）再触发一次，5 级最多 5 颗、二星最多 6 颗，期望 3.3 颗。
  4 颗金 = 360，覆盖 78% 的触发轮次；再往上加（450/540）只多 4% 总收益，却让整局
  消费次数从 6 次掉到 5 次。详见 `constants.WEEKEND_WORK_MONEY_GATE` 的注释。
- **训练流（2026-11-11 起）**：不再固定「周六步行街 → 游戏厅 → 公园」。
  按**精力缺口**（上限−当前）选动作：
  - 缺口 ≥ **30**（`周末划船缺口`）→ 公园；公园里缺口 ≥ **70**
    （`周末野餐阈值`）选野餐，否则划船；
  - 缺口 < 30 → **餐厅打工**；打不了工时公园兜底（划船拿属性）。
  - **训练流不再去步行街/游戏厅**：那两处是「花一天 + 花零用钱」换一张卡，
    打工是「花一天 + 赚 240~420 零用钱」，而商店买牛奶/秘籍**不占日期** ——
    特训牛奶 50 币能让 3 天训练少耗 40% 精力（约 1 个训练日），对训练流更划算。
  - 缺口读不到 → 回退「餐厅 → 公园」，不再回退旧的步行街行程。
  - 训练日休息阈值同步调到 **50**（50+ 失败率 0%，47/49 已 11%/27%）。
  - **第3周周末例外（2026-11-13）**：第4周海边合宿第4天是玩家等级增益给的
    「全队友参与」训练，前一天体力不够就得休息、错过这一天。所以第3周周六/周日
    要把体力拉回 ≥ `vacation.stamina_target`（`strategy/params.json`，默认 **100**）：
    体力不够时把餐厅打工改成公园；公园按「离目标还差多少」选野餐/划船。
    周六 <30 必须先去公园；周六 <55、周日 <125 不打工（打完就回不到 100）。
    读不到体力时只去公园，不赌。
- 读不到星期时，商店流仍按**周六那一行**兜底；训练流按缺口、扭蛋流 / 小游戏流不看星期。

- **商店**：**只要有「新品上市」标签就进店**（2026-11-08 起**不分周数**；橙色标签挂在
  右上角商店按钮**正上方**），周末首页同样先点「商店」再点「出行」（见 §4）。
  一天只真进一次（`_shop_day`，确认看到商店页才记账）。
- **别把地图当内页**（2026-10-31 实跑）：地图上除了地点名还有各自的奖励提示
  （属性+ / 精力+ / 零用钱+ / **扭蛋增强**）。只靠单个关键词的内页判据会被这些提示抢走 ——
  `handle_street` 就曾因为地图上的「扭蛋增强」把地图判成扭蛋页，进去读不到卡就退出，
  当天的出行白跑。现在判据里加了「地图上 ≥2 个地点名 → 不是内页」的门，
  且 `mark_visited` 必须放在确认真的是内页之后。
- 一天只进一个地点；进了发现不合适就退出，**当天不再重复进同一个地点**
  （`weekend_state["visited"]`）。
- 训练流的缺口规则已收进 `training_weekend_places`：缺口 <30 → 餐厅打工，
  缺口 ≥30 → 公园（见上一条）。训练流不再经过「两个地点开关」那段逻辑
  （它的候选里没有步行街/游戏厅）。
  旧的 `WEEKEND_PARK_GAP=60` 双关规则只用于其它流派。
- **队友气泡**（`BaseGirlsTask.venue_has_mate`，深藏青像素占比 ≥ 0.02，
  标定：有气泡 0.052~0.096、公园 0.0010）：判据保留，`tools/check_mate_bubble.py`
  和单元测试仍用它校验界面识别，但**不再参与地点选择**（2026-11-10 用户口径）。
- 打折判据 `venue_on_discount`：OCR 到「打折」且框在名字左侧同一行。
- **隐藏规则**（2026-10-30 用户口述）：在步行街买扭蛋 / 在游戏厅玩小游戏，**当天就结束**，
  所以这两处是二选一；某些角色能突破（例：羽漱川湊 游戏厅可买两次）。

## 1.1 餐厅打工的选项（2026-11-03，通用）

实现：`handle_restaurant` / `restaurant_order` / `restaurant_preference` / `card_mate_counts` / `option_selectable` / `card_stamina_cost`

| 顺序 | 规则 |
|---|---|
| 1 | **能选的优先**：卡片附近写「精力不足 / 无法选择 / 不可」→ 不可选；卡片标的消耗 > 当前精力 → 不可选 |
| 2 | 两张都能选时：默认选**当服务员**（右边、耗精力、零用钱++） |
| 3 | **桌游GM**（左边、不耗精力）的队友比当服务员**多 2 个及以上** → 改选桌游GM；只多 1 个仍选当服务员 |

- 当服务员默认按 `WORK_STAMINA_COST`（25）估消耗、桌游GM 按 0；卡片上写了消耗以卡片为准。
- 「精力+30 / 精力恢复」这类是收益，不会被当成消耗。
- **队友个数按「脸」数**（2026-11-03，`parsers.mate_face_count`）：现版本的队友条是
  「深蓝胶囊 + chibi 头像」，旧判据（深蓝连通块）只能给「有 / 没有」，
  `docs/shots/restaurant_cards.png` 左卡实际 2 人、右卡 1 人却都读成 1 → 平局。
  现在按「很亮的暖肤色连通块」数人头（同一张卡的头像之间隔着头发，不会粘成一块），
  **只要有一张卡数到脸就只认脸**；整页一个脸都没数到（旧版深蓝圆标记的界面）才退回
  旧的「有/没有」判据 —— 那个兜底分不清「队友标记」和「卡片自己的深蓝图标」
  （2026-11-03 20:37 实跑：当服务员头顶 0 个脸，背心图标却被记成 1 个队友，
  「2 人 vs 0 人」读成「2 人 vs 1 人」，规则永远差 1 个不触发）。
- 名字认不出（OCR 截断）时按位置理解：右边当服务员、左边桌游GM。
- **精力读的是整帧 OCR**（`top_bar(texts)`，2026-10-31 改）：裁剪顶栏重 OCR 会把
  `0/130` 读成 `301130`（斜杠被吃掉）→ `stamina=None`，这条规则就静默失效了。
  那一天实跑：精力 23/130 仍然去点 25 的「当服务员」，卡在灰掉的「前往」上 4 分钟。
- **卡片页本身不显示精力消耗**（2026-10-31 实测帧 `docs/shots/restaurant_cards.png`）：
  只有进了详情弹窗才看得到「精力不足 ⚡25」。所以 `handle_activity_go` 必须兜底：
  弹窗说不足 / 同一个「前往」点了没反应 → 关弹窗 + 把这张卡记进
  `blocked_activities()`（当天不再选），回卡片页改选另一张（桌游GM 不耗精力）。
  两张都点不动才退出餐厅。


## 2. 扭蛋（步行街）

实现：`handle_street` / `read_gacha_cards` / `card_band_quality`

| 条件 | 行为 |
|---|---|
| 品质是蓝/其他 | 不买 |
| 品质 **彩/金/紫** | 候选；分数按配置 `扭蛋品质优先`（默认 彩 400 / 金 300 / 紫 200） |
| 同品质时的取舍（2026-11-07） | 先「增强款」→ 再「有队友加成」→ 再「**非恢复优先**」（同等条件恢复精力的优先级最低，用户 2026-11-07 口径，取代 2026-11-03 的「恢复价值排最后但同分要赢」）→ 最后「便宜的」。**恢复量不进 score** |
| 名字带「+」 | **不算分**（用户 2026-11-02）：「+」只代表**同名卡片**之间的档位差，没「+」的同名卡本来就是紫/蓝，已由品质体现 |
| 效果是「清空/消耗所有精力」且精力 ≥ 30 | 不买 |
| 效果是「清空/消耗所有精力」且精力 < 30 | 可以买（拿精力换属性） |
| 效果是**恢复精力**（见下） | 先过**三类资格门槛**（2026-11-08 用户口径，见下节），过门槛的也只是「非恢复优先」垫底候选，不是同分要赢 |
| 零用钱 < 卡片价格 | 跳过，看下一张 |
| **读不到价格**（价格数字还没渲染出来） | 不买，继续等；等不到就退出 |
| 读不到卡片（开局动画/页面切换） | 原地等最多 3.2 秒（0.8s×4）重试，仍空才退出 |
| 所有卡片都不满足 | 点右上角返回，**不点确定** |

阈值 `扭蛋清空精力阈值` 默认 30（`default_config`）。

### 卡面特征（2026-11-02 01:08 实拍，1549x871）

帧：`logs/events/1102-010859_gacha_teammate_middle.jpg`（第6周 星期日，105/130，471 币，
三张卡 70 / 90 / 50 全打折）。用线上同一份 `TrainingParsersMixin` 跑这一帧的实测值：

| 特征 | 取法（代码位置） | 实测 |

### 卡片怎么定位（2026-11-01 修）

卡片**优先靠价格药丸定位**（每张卡底部一个 60/80 的数字）。但价格数字是
**晚于卡面渲染**的：2026-11-01 15:09 实跑里，卡面文字（`训练增强`/`运控增加+++`）
已经画出来了，价格还没画出来 —— 旧代码「没价格 = 没卡」，于是：

- 读不到卡 → 等动画的逻辑以为页面是空的 → 退出 → 白丢一次扭蛋；
- 等动画的旧阈值（连续 2 拍读不到就退出）正好卡在这个**中间态**上。

现在：

1. 没有价格时，改用**卡名行**（`投射增加++` 这种，落在标题带 `GACHA_TITLE_BAND`）
   按列聚类反推列中心 → 卡照样认得出来，`price` 为 `None`；
2. `price is None` 的卡**不作为候选**（买不起点「确定」会卡在扭蛋页反复点），
   而且不算「卡片已稳定」→ `settle_gacha_cards` 会**继续等**；
3. 连续读不到卡的阈值从 2 拍放宽到 4 拍（`GACHA_EMPTY_LIMIT`，约 3.2 秒）。

### 专注怎么读（`/` 被 OCR 读成 `1`）

`57/130` 常被读成 `571130`、`30/130` → `301130`、`17/115` → `971115`
（斜杠那一格被当成数字 1，周数还可能粘在最前面：`3 251130` = 25/130）。
`top_bar` 现在两层兜底（实现见 `TrainingParsersMixin.top_bar`）：

1. **拆粘连串**：末 3 位当上限（100~200），前面的数字枚举所有连续子串当「当前值」候选；
2. **专注条仲裁**：顶栏药丸 = 黄色填充段 + 灰色空段，总宽和左沿是固定版式
   （`0.2885w` / `0.2010w`，1920/1549/1307 三种画面完全一致），填充比例换算专注
   与 OCR 正读值逐帧相等（58/115、40/115、50/115、75/121、61/121、87/117、94/130、57/130），
   用它在候选里挑最近的那个（容差 5）。

只在 OCR 解不出专注、或与像素差 > 2 时才改判；上限没读过就返回 None（不猜）。
同一帧结论缓存一次，避免两次调用给出 56/57 两个值。

### 星期几怎么读（会被 OCR **丢字**，2026-11-02 实测 1136 帧定案）

用户反馈「星期一 星期二 的识别有问题」。查完 1136 张存证帧的结论：

| 结论 | 数据 |
|---|---|
| 整帧 OCR **从来没读错**星期几 | 能读出来的 1023 帧，值 100% 正确 |
| 问题全是**丢字** | 丢字率 9.9%（1136 帧里 113 帧读不出星期几） |
| 丢字率**跟笔画数成反比** | 星期一 67.7% / 星期二 0% / 星期三 0% / 星期四 0% / 星期五 0% / 星期六 7.5%（读成「期大」）/ 星期日 0% |

原因看像素就明白：**「一」只有一条横线**，OCR 的检测框把它并进「期」里，
整词于是变成「星期」两字（框里只剩「星期」/「星期-」）。
「二」有两条横线、「三」三条，笔画够，不会丢。

**所以「二」本身没问题** —— 166 张「星期二」的帧全部读对。
真正读不出的是「一」（67.7%）。裁图人工核对 117 张残框帧，
**全部**是「星期一」，没有一张是「二」。

丢字形态一共 4 种：`星期`(70) / `星期-`(38) / `期日`(12) / `期大`(5=星期六)。

**兜底**（实现见 `src/tasks/ui/topbar_day.py`）：
`top_bar()` 读不出星期几时，把那块裁出来放大 3 倍**重读** ——
检测阶段会重新切分，单独那条横线就成了独立的框，识别成「一」。

- 区域位置：归一化 `x 0.092~0.192, y 0~0.075`（实测框在 `x 0.1014~0.1762`，两侧留余量）
- 放大倍数 **3**：实测 x3 在 1031 帧上与整帧 OCR 100% 一致；x4 起开始丢（x5 有 6/51 读不出，x6 连「星期二」都掉）
- 判据**只认整词**「星期X」（三个字，不多不少）：正文里的「星期日要训练」「比赛后期」都不算
- 读不出就返回 None，**绝不猜** —— 猜错会让 `day_state()` 整个重置

效果（`tools/check_topbar_day.py` 离线回归）：
整帧读得出的 1065 帧，区域重读 **100% 一致**（兜底不改已读对的结论）；
整帧读不出的 117 帧，区域重读救回 **116 帧（99.1%）**。

### 品质色怎么判（2026-11-01）

- **彩色**（训练等级提升后解锁）的卡头是**整条彩虹渐变**，中位色相落在紫区
  （实测帧 `logs/now.jpg` 中间那张 `体能增加+++` H≈121），只按中位色相判就会当成「紫」，
  于是被金卡压掉 → 点错。现在 `card_band_quality` **先认彩虹**：
  色相 30° 一档，**≥3 档各占 ≥10% 且最大档 < 0.70** → 彩。
- 单色卡过不了第二条：同帧两张金卡最大档 0.96~1.00，紫/蓝同理。
- 游戏厅卡面（`card_quality_at(..., rainbow=False)`）不判彩色，免得上高光被误判。

### 恢复精力卡的关键字（2026-10-27 用户截图）

金卡「**精力恢复++**」是当前收益最高的一类，OCR 写法：

```
立刻恢复90精力，之后每天恢复30点，持续4天，队友属性大幅提升
```

- `stamina_recover()` 只认两类片段：`恢复<N>精力` / `恢复<N>点`，以及
  `每天恢复<N>点…持续<D>天`（N×D）。上面这张 = 90 + 30×4 = **210 点**。
- 含「清空 / 消耗」的卡一律按 0 计（相反效果），绝不与恢复卡混淆。
- 评分：`min(恢复量, 精力上限 - 当前精力) × 0.5`，**只在多张恢复卡之间**比高下
  （2026-11-07 用户口径：同等条件下恢复精力的优先级最低，属性卡恒排在前面）。
- 识别不到顶栏专注（`stamina=None`）时不分恢复加成，保持旧行为。

### 恢复卡三类资格门槛（2026-11-08 用户口径，`places/street.py: recover_rejected`）

| 类型 | 判据（效果文本） | 门槛 | 不过门槛 |
|---|---|---|---|
| ① 立刻恢复 | `立刻恢复<N>精力` / `恢复<N>精力`（混合卡只数立刻段，`stamina_recover_immediate`） | 当前 + N ≤ 上限（超了就是溢出，回不上的白花钱） | 拒买，日志带「溢出」 |
| ② 全部恢复 | 「恢复全部/所有精力」（`GACHA_FULL_RECOVER_PHRASES`，2026-11-08 日志还没出现过这类卡，词表按口径先建） | 上限 − 当前 > 100（缺口太小不值一张卡） | 拒买，日志带「缺口 N ≤ 100」 |
| ③ 接下来几日恢复 | 只有 `每天恢复<N>点…持续<D>天`（没有立刻段） | 当前 / 上限 < 1/2（精力还剩一半以上时不缺这几天的） | 拒买，日志带「≥ 一半」 |

- 读不到精力/上限（顶栏 OCR 抖动）→ **不拦**，按老规则买（同「第 7 周周数读不到不过滤」口径）。
- 拒绝理由写进扭蛋 detail 日志（`·溢出…` / `·缺口…` / `·≥ 一半`），方便复盘调阈值。
- 排序（2026-11-07 口径）：品质 → 增强款 → 队友 → **非恢复优先** → 恢复价值 → 价格。
  2026-11-08 修：判「是否恢复卡」从 `recover > 0` 改成按效果文本
  （`is_stamina_recover_card`）——「精力补充」这类**全部恢复卡 recover=0**，
  旧判据把它当非恢复卡、反而排在所有恢复卡前面（模拟 20/130 时压过三张精力恢复）。

  - 周数读不到时不拦（OCR 抖一帧不能把采购整拍废掉）。

    属性缺口（缺口排除阈值）、`soft_cap` 减半、余额、0 元规则照旧。
    买不到属性（缺口都够了或钱不够）就关店。蓝/白商品的详情面板也照读，
    避免只看名字表漏掉属性卡。

## 6. 训练科目

实现：`handle_subject_select` / `scoring.py`

- 评分 = 队友数×1.0 + 器材数×1.0 + 经理×**2.1** + 金框×**1.2** + 彩框×**2.3**。
  （2026-10-29 用户口径：彩框抬到 2.3，压过经理 —— 有彩框就该练。
  金框/彩框指**训练科目按钮外面那一圈**（装备、经理经验满了会点亮），不是器材卡上的框——
  按器材卡的金框再算一次会和「器材数」重复计分（用户 2026-10-27 口径）。
- **彩框判据**（2026-10-31 两次重标定，`parsers.has_crit_border`）：只采以该行文字为中心的
  **上下两条边**、x 0.74~0.98w、半窗 **±0.050h**，品红/绿像素占比 ≥ **0.13**

- `满经验`（器材卡 MAX）在日志里会给出来，但**不进评分**（框已经代表「满经验点亮」，
  再算一次会重复计分）。
- 先只看**有队友**的科目，按屏幕从上往下逐个探测。
- 排序：分数 → 队长推荐属性 → 当前数值低的（成长空间大）→ 屏幕上靠前（兜底）。
- 失败率 > `失败率上限(%)`（默认 50）→ 退出科目页并强制休息（`_force_rest`）。
- 训练日精力 < 阈值 → 休息（`flow.rest_threshold`）：
  - 平时：`休息精力阈值`（默认 40）；
  - **周四**（2026-11-04 用户口径：原来的「周二 65」改到这里）：**扭蛋流 / 小游戏流**
    有硬阈值 **60**（`THURSDAY_REST_THRESHOLD_BY_STYLE`），取 `max(配置值, 60)`；
    **训练流 / 商店流周四没有任何特殊限制**，只遵守 `休息精力阈值`；
  - **周二没有任何特殊阈值**（旧的「周二 65」「周二一律 60」都已删除），

|---|---|
| 「多角色」是什么 | **多局串行**，不是一局内换人。一局 = 一次养成，终点是「注册球员 → 回大厅」 |

### 界面上的「刷到目标分」（2026-11-11 用户口径）

- 不勾「指定队长」= 接手一局没打完的训练；勾了「刷到目标分」时，
  日历认出队长后由 `flow.adopt_calendar_captain` 把「指定队长」写成这个人，
  再 `init_captain_queue()` 派生 `"队长:目标分"`，接着练到分停。
- **一局结束**读一次勾选（`flow.advance_queue_after_round`）：中途取消 =
  这局跑完就停；下一局开始前再勾上 = 继续。运行中才勾、本局没有队列 →
  界面提示「下次【开始】生效」，不在中途补建队列。
- 局末还会按**界面当前值**重算下一局刷谁：中途换队长 / 改目标分，
  本局不变，下一局就换（用户 2026-11-11 口径）。
- 局末发现「指定队长」被取消（空）→ 这局跑完就停，不再按旧队长续跑。
- 没勾「刷到目标分」→ 不写「指定队长」，保持接手模式，这局跑完就停。

- 配置只有一条字符串：`队长队列 = 野上泷:7500,亚理纱·贾斯敏:7300,近江奏:7300`
  （解析在 `queue.parse_queue`，中英文逗号/分号/换行都收）。**不给每个角色单独加配置项**。
- `多角色队列` 关掉 / 队列解析为空 → 全程老行为：只练 `指定队长`，跑完一局就结束。
- **`单局最大操作数` 是按局算的**（`run_one_round` 开头 `self._steps = 0`），
  多局连跑不会撞上限 —— 旧版它是「一次 run」的上限，多角色下第一局就会把额度吃光。
- 换队长必须**同时**清流派（`_style/_style_name/_style_pending`）：流派是队长的属性，
  不清就会拿上一个队长的周末计划/休息阈值去跑新的一局（见 §0）。
- 队长池里没有这个角色时，现在的行为是「弹窗 + 停任务」（`entry.handle_captain`）；
  多角色下这就是**唯一**允许停任务的情况 —— 队列里其它角色不会替它继续。

## 16. 六维面板读数：一条护栏 —— 值必须 ≤ 这一格的上限（2026-11-04）

实现：`training/parsers.py: attr_value_from / read_attribute_values / refresh_attr_info`、
`src/ui/MonitorTab.py: ATTR_KEYS`

用户反馈（2026-11-04）：监控页六维跟游戏不同步，「分数预测」突然跳到 1w4、一会又 9k。

| 事实 | 说明 |
|---|---|
| 每格写法有四种 | `投射B488/1680`、`3488/1680`（等级粘在前）、`体能B 464/+16`、`意识C 261/1689` |
| 事故读数 | `体能 8116`（真值 1016）、`意识 3114`（真值 1114）—— 旧判据「取这行第一个 ≥100 的数字」直接采信 |
| 为什么「跳完还挂着」 | `info["attrs"]` 是**合并**语义（缺一项时保留上次的值，免得被气泡遮挡打回「—」），所以一次读错会挂到下次进休息室 |
| 护栏（只有一条） | **这一格的值必须 ≤ 这一格的上限**：上限取本帧的 `/1680`，没有就用上次记下的（`_attr_caps`，一局内不变）。两个事故值都超上限，一条规则全覆盖 |

- 误读的处理是「**这一格不动**」，不是「猜回去」：不砍前导位（`3488` 不当成 488）、
  不拿「上次的值 ±窗口」二次判（上一版那样写，规则太多）。下一帧读干净了自然补上。
- 快照时机没变：只在「进休息室（训练日主界面）」拍一次（`handle_training_day` →
  `snapshot_lounge`）；科目页 / 周末 / 比赛日不读也不反推。
- 「分数预测」= 六维和 + 技能分，**六维不齐 6 项就不算**（显示「—」）：
  合并语义下通常一分钟内就齐，只有换队长后的头一拍会短暂空着。

## 17. 放大重读模块（2026-11-04 用户口径：「故障多发的就用这个方法重判」）

实现：`src/tasks/ui/zoom_reread.py`（裁 → x3 → 重跑 OCR → 置信度过滤）

**OCR 出错多半不是「认错字」，是检测框把边界划错了**，放大后检测会重新切框：

| 真实内容 | 整帧 OCR | 病根 |
|---|---|---|
| `星期一` | `星期` / `期日` / `期大` | 「一」只有一条横线，被并进「期」的框（丢字率 67.7%） |
| `B1016/1680` | `8116` | 评级 `B` 并进首位，B 的两个弧 + 1 的一竖 ≈ 8 |
| `3 488` | `3488` | 等级数字粘在数值前面 |

- 实测收益：整帧读不出的 117 帧「星期几」，x3 放大重读救回 **116 帧（99.1%）**。
- **同一个格子，整帧跑和单独裁出来跑，结果不一样**（2026-11-04 实测
  `logs/unknown/1104-102229_unknown_s25.jpg` 的投射那一格）：

  | 读法 | 结果 |
  |---|---|
  | 整帧 OCR（线上现状） | 粘成一个框：`3488/1680` |
  | 只裁这一格再 OCR | 切成三个框：`B` / `488` / `8/1680` → **数字是对的** |

  原因：评级字母 `B`/`C+`、等级数字、`⚡` 图标和数值同一基线，间隙只有几个像素；
  整帧按固定高度缩放后间隙被压没，检测就连成一条。所以「放大重读」的本质是
  **给这一小块单独一次、切得更准的识别** —— 不是靠模型多聪明。
- 反过来，**手工往左收边（trim）没有收益**：实测左收 12% 只是把评级切成碎片、
  左收 20% 会把 `体能` 读成 `1717`。范围由检测自己重切才对，不要手写 trim。

- 放大倍数 **x3**（x4 起「星期一」开始丢，x6 连「星期二」都掉）；置信度下限 0.30。
- **同一机制只此一处**：`ui/topbar_day.py` 原来自己写了一份（`crop_region` +
  `_ocr_boxes`），2026-11-04 已改成调本模块；以后谁要重读都调它，别在 parsers /
  handlers 里再抄一遍。
- 两条使用约定：① **只用来读值，不用来找点击位置**（缩放坐标换算最容易错，
  要点击继续用整帧 OCR 的框）；② **只在读不准时才调**（读不出 / 超上限 / 丢字），
  一次多花约 0.1~0.2 秒，裁得越小越便宜。
- 已接入：`topbar_day.read_day / read_week`（星期几、第N周）、
  `parsers._attr_values_reread`（六维面板**读不准的那一格**单独裁出来重读，
  不是整块面板）。
