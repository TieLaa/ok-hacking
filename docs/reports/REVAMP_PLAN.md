## 三、设计：8 个决策点

一个 `Style` 基类给通用实现，四个流派只覆盖差异（不写全量表，避免 4 份重复）。

```python
class Style:
    name = ""
    money_floor = 300
    shop_visits_per_day = 1

    def pick_subject(self, ctx, boxes, previews): ...   # 科目优先序
    def should_rest(self, ctx): ...                     # 练还是休
    def wants_shop(self, ctx): ...                      # 现在进不进店
    def pick_item(self, items, ctx): ...                # 店里挑哪件
    def plan_outing(self, ctx): ...                     # 出行去哪（有序）
    def park_option(self, ctx): ...                     # 公园做什么
    def plan_team(self, ctx): ...                       # None = 自动选择
    def use_flow_switch(self, ctx): ...                 # 用不用「跳入其他流程」按钮
```

- `ctx` 是每拍重建的普通 dict（星期/周/剩余天数/专注/零用钱/失败率/六维/今日已做），**不做累计账本**——任务随时会被重启，累计状态一定错位。
- 资源分配落在这几个点上：时间 = `plan_outing` + `shop_visits_per_day`；精力 = `should_rest` + `park_option`；钱 = `money_floor` + `pick_item` + 赛前一天清空。
- 跨天只有两条规则，写在基类：`days_left == 1` 清空零用钱、最后一天优先训练。不做前瞻规划。

判据改造（两处，别扩大）：

1. `handle_daily_shop` 删掉「有出行就不进店」的绝对排除，改成「有出行**且没有休息按钮**」才排除；
2. `handle_go_out` 的「有出行 = 周末首页」降级为「有出行 = 可以出行」，是否点由策略决定。
   （这一条等有周末首页截图再动，现在动会搞坏周末流程。）

## 四、会影响设计的三条事实

1. **改期角色入队即常驻**：训练日有出行、周末有训练是常态。所以判据必须永远「看按钮不看日期」，代码里不该有「有没有该角色」的分支。
2. **同一张地图 + 一个跨流程跳转按钮**：地图页只有一个，`handle_weekend` 与 `handle_go_out` 后续应合并。跳转按钮的实际行为未知（没有角色、开服资料少）——**默认关闭 + 观测日志**，不预写逻辑。风险：跳转若改变顶栏日期，`weekend_state` 会按 `(week, day)` 重置，「今天去过」会被清空。
3. **商店件数**：原本 4 件 → 全局强化 +1 = 现在 5 件（3+2）→ 角色入队可能 +1 = 6 件（3+3）。
   网格 3 列固定宽（列中心 0.223/0.357/0.490，间距 0.134），第二行价格 y=0.746。
   买完**即时刷新**（与扭蛋一致），所以不要加 Session/状态机——现有「一拍买一件、下拍重读」就是对的形状；
   要改的只有「今天已逛过」这个布尔去重（改成计数，配额由策略给）。

## 五、被否掉的方案（不要重走）

| 方案 | 否掉的理由 |
|---|---|
| 动作目录 + 优先级打分器 + 预算账本 | 四个流派、每天两三个动作，用规划器替代 `if` 只是把复杂度搬家；优先级数字一改全流程行为变，难调试 |
| `ShopSession` 状态机 | 主循环本来就支持刷新，加状态机破坏「单拍一个动作」这个唯一稳定的心智模型 |
| 「能力集合」抽象层 | 判据直接看「这帧有什么按钮」就够了，不需要额外一层 |
| slots / max_times / 配额模型 | 游戏里一天能做几件事没验证过，全是猜的 |
| 前置条件不满足就降级流派 | 静默改行为，用户以为在跑商店流其实在跑训练流；应该是少做一个动作，其余照跑 |
| 每个流派一张完整优先级表 | 70% 决策相同，应该「默认实现 + 只覆盖差异」 |
